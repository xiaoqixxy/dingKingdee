# 明细表同步

## 配置流程

选择连接 → 选择表单 → 选择明细表及同步方式 → 筛选排序 → 提交。

- `/api/formSchema` 使用与 `/api/sheetMeta` 相同的请求结构，额外返回 `entryOptions`。
- 选项来自 `Entrys` 中的 `EntryEntity`，使用中文名称显示，使用 `Key` 保存。
- 每份配置仅选择一个明细实体；空选择继续使用原单据头模式。
- 缺少主键或具有非表头父实体的多层明细不可选择。
- 筛选、排序只能使用表头及当前明细字段。切换实体时清除失效条件。
- 钉钉 `/api/sheetMeta` 响应不包含配置界面使用的扩展元数据。

新增保存参数：

```json
{
  "configVersion": 2,
  "selectedEntryKey": "FEntity",
  "headerFillMode": "FIRST_ROW"
}
```

`FIRST_ROW`：每张单据筛选后的第一条明细填充表头，其余行显式返回空字符串。
`ALL_ROWS`：每条明细均填充表头。
没有 `selectedEntryKey` 的旧配置仍走原同步逻辑，不需要数据库迁移。

同步参数通过已有 `saveConfigAndGoNext` 交给钉钉保存；连接凭证表没有新增完整同步方案存储功能。

## 查询与分页

- 业务逻辑不硬编码具体业务字段 ID。表头通过 `EntityType=HeadEntity` 识别，实体关系使用元数据中的 `Key`、`ParentKey`；字段、主键、序号和辅助属性子字段分别取自数据字典。允许保留 `.FName`、`.FNumber` 等通用关联属性规则。
- 表头与明细共用同一字段及值转换逻辑：日期、数字、枚举、布尔和文本保留对应的类型与格式；实体名称仅作为明细字段的显示前缀，不改变类型。
- 测试用例、实测脚本和说明中的具体字段 ID 仅为测试数据或示例，不参与生产查询规则。

- 对外明细字段 ID 使用实体前缀，金蝶实际查询使用单独的 `queryKey`。实测 `ExecuteBillQuery` 普通业务字段使用 `FQty`、`FMaterialId.FName`；主键和序号使用 `FCRMContractEntry_FEntryID`、`FCRMContractEntry_FSeq`。筛选排序同样转换为实际查询标识。
- `FlexFields` 辅助属性组合按元数据展开为子字段，例如版本号查询路径为 `FAuxPropId.FF100001.FNumber`，不能将组合容器作为 `FAuxPropId.FName` 查询。
- SDK 返回的单行错误对象在记录转换前识别，直接返回金蝶业务错误，不再误报为正常数据或仅报告列数不一致。
- 早期未带前缀的明细字段配置需要重新选择明细并提交，筛选排序中的失效字段会被清除后重新配置。
- 表头排序、单据内码、明细排序、明细序号、明细内码组成稳定的分组排序。
- 查询条件增加明细内码大于零，无明细单据不产生空明细记录。
- ID 由账套、表单、明细实体、单据内码、明细内码生成，与填充方式无关。
- 继续使用数字分页位置。非首页从上一行开始读取，以判断跨页是否延续同一单据；多读一行判断后续页。
- 权益上限按实际明细记录计数，按剩余额度截断，不添加提示性质的假记录。
- 源数据在分页期间变化仍可能影响 offset 分页；本次没有引入数据库快照。

金蝶字段路径参考：[WebAPI 查询单据体分录内码、序号](https://vip.kingdee.com/article/27491)。

## 验证

后端：在仓库根目录运行 `mvn -pl ding-server -am test`。

前端：在 `ding-web` 目录运行 `node scripts/test.js --watchAll=false --runInBand` 和 `npm run build`。

后端测试使用用户提供的费用申请单元数据，覆盖单选、兼容、跨页、重试、限额、筛选后首行及非法参数。
前端测试覆盖单选、两种方式、失效条件清理、无明细、元数据错误以及提交参数。

本地浏览器调试可在后端测试生成 `target/detail-debug/schema.json` 后，运行仓库下的 `node output/detail-debug.cjs`。
此调试脚本使用本地模拟连接及服务器转换得到的元数据，不请求生产接口。页面为 `http://localhost:3017`。
缺少钉钉运行环境时初始化错误与提交提示是预期行为；没有修改钉钉初始化逻辑。

正式构建默认保持工作区原有 API 地址，可通过 `REACT_APP_API_BASE` 覆盖。上线时先部署支持 `/api/formSchema` 的后端，再部署前端。
