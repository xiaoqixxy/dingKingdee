# 同步回调日志（旧单页版本）

此文记录旧版实现；当前批次汇总、分页重试及完整堆栈机制见 [sync-batch-logging.md](sync-batch-logging.md)。

## 原因与入口

`POST /api/records` 原先只调用金蝶并返回结果，没有调用日志持久化服务。
后台已有 `ding_sync_execution`、`ding_sync_execution_item` 和 `ding_api_call_log` 查询页面，因此即使同步成功，页面也不会出现记录。

现在验签通过且企业ID有效的回调，会先独立提交 RUNNING 执行，再访问金蝶。结束时在一个新事务中保存执行终态、返回记录ID和接口调用日志。空结果也保存 SUCCESS；查询/转换/分页参数异常保存 FAILED；限额截断保存 PARTIAL。耗时使用单调时钟。

## 统计口径

- 一条执行 = 一次分页回调。协议未提供经确认可跨页复用的整次同步标识，不能按企业或表单猜测合并。
- `request_key` 是本次投递尝试生成的唯一键；原始 `requestId` 仅保存在白名单摘要。同一个 requestId 的再次投递单独留痕，不做业务去重，也不推测重试关系。
- SUCCESS/明细 SUCCESS 表示源记录已准备返回，不表示钉钉最终入表成功；没有目标入表确认回调，目标记录ID保持为空。
- total/success 只统计实际返回的数据行，限额提示不计数。查询前或转换阶段失败时，无法确定失败记录数，所以计数为0，错误保存在执行级别；不伪造失败明细。终态满足 total=success+failed+skipped。
- 每页最多300条返回明细。头表模式沿用原有上限提示语义；明细模式用额外查询行判断限额截断。
- 新日志只写新模型，不写兼容 `ding_sync_log`。旧表月用量与首页旧统计不改为累加新表，避免重投和双写造成重复计费。新执行条数不能直接作为计费依据。

## 隐私、异常与可见性

请求摘要只包含 requestId、分页位置、每页数量、金蝶源表单ID和口径标识。响应摘要只包含条数、是否有下一页和口径；不写凭据、过滤条件或业务字段内容。错误保存分类摘要，不保存上游原始报文。同步查询的原始参数控制台打印已移除。

金蝶SDK没有提供可靠HTTP状态/业务码，这些字段保持NULL，不能伪造200。`records`日志记录返回给钉钉的业务码0/10005。后台执行详情展示同企业同执行的接口时间线，需同时具备执行列表和接口日志权限。

日志库不可用时，不返回无记录的成功：开始写入失败时停止查询，结束写入失败时回调返回错误并打印 `SYNC_LOG_PERSIST_FAILED`（含traceId/executionId）。开始记录保留RUNNING便于核查。服务被强制终止也可能保留RUNNING，不能据此自动判断上游同步失败或成功；此版本不自动重放、不伪造终态。

无有效企业ID、签名不通过或JSON根结构不可解析的请求，无法建立可信企业归属，不写业务日志。签名行为保持原有入口规则。

## 发布顺序

1. 先确认原有日志模型迁移已执行，存在上述三张表。
2. 执行 `sql/sync-execution-callback.sql`，让 sync_form_id 可空。这是可重复执行的列定义调整，不修改历史行值。回调只带金蝶源表单ID，不能把它伪造为 ding_sync_form 的外键。
3. 构建并发布后端与后台前端。本次没有操作远程数据库、发布或重启正在运行的服务。
4. 发起真实同步，在“日志中心 → 同步执行记录”查看新执行；详情应有记录ID和 QueryBusinessInfo / ExecuteBillQuery / records 调用。查询失败和零条结果都应出现执行记录。

日志时间沿用当前数据库/应用已有的时间约定，不在本次引入UTC转换或历史时间回填。发布时应维持JVM/JDBC/数据库时区一致。之前未写入的同步记录无法从本次改动恢复。

## 验证

新增单元测试覆盖成功、空页、异常、嵌套超时、非法参数、无企业、限额提示、重复投递与数据库失败。H2 MySQL兼容模式测试验证MyBatis SQL、生成主键、明细关联、计数、终态重复更新拒绝和结束事务回滚。H2不替代生产MySQL迁移演练；未对真实钉钉/金蝶发起同步。
