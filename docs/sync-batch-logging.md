# 同步批次日志与完整堆栈

## 批次关联

首个 `/api/records` 请求创建总日志，后端将批次随机链路号和分页位置编码为 `s1:<traceId>:<offset>`，放入响应的字符串 `nextToken`。钉钉原样回传后，下一页复用同一总日志；不按时间窗口或企业+表单猜测合并。控制器仍将整数offset传给金蝶，编码只用于钉钉与本服务之间。

每次分页请求都创建 `ding_sync_execution_page` 尝试记录。成功完成一页后，在同一事务内更新总条数、成功页数、记录明细及接口日志。第一页300条、第二页300条、第三页45条，对应一条645条的总日志。总日志在 `hasMore=true` 时保持RUNNING，最后一页结束后成为SUCCESS或限额PARTIAL；中途失败保留之前的成功条数。

批次关联同时检查签名入口、企业ID、数据源配置哈希和下一页位置。不同企业或变更后的源配置不能复用旧令牌；不同首次requestId产生独立批次。同一个首次requestId和源配置再次投递时，复用原批次。没有requestId的首次回调不能可靠识别重投，独立建批次。

## 重试与并发

- 数据库锁定总日志行，确保同一页只有第一次成功计入总数；所有重投尝试仍有分页与接口日志。
- 完成失败后可用原分页令牌重试，成功后总日志恢复正确状态；原失败堆栈仍保存在该分页及接口日志中。
- 整页成功前无法知道具体哪些源记录失败，所以不伪造失败条数或失败记录ID。
- 累计耗时是各分页尝试的处理耗时之和，包含失败和重试，不包含钉钉两次请求之间的等待。
- 这仅是日志计数去重，不是业务数据快照或接口响应缓存。源数据在重试时变化仍可能改变返回内容，沿用既有offset分页语义；不能据此承诺钉钉恰好入表一次。
- 服务进程异常终止或日志落库失败时，已提交的RUNNING日志保留用于排查，不伪造成功/失败终态。

## 堆栈

执行总日志、分页尝试和接口日志均增加独立 `LONGTEXT error_stack`。标准Java堆栈保留异常类、代码行、cause链、suppressed异常和换行；不按1000字符截断。摘要仍为最多1000字符。后台列表不加载大堆栈，详情可展开查看；分页尝试和接口时间线均支持翻页。

写入数据库、返回错误、输出应用日志前，对已知APP_SECRET等凭据、密码/令牌键值、认证头和URL进行脱敏。业务报文不作为单独字段写入日志；如果异常本身带有内容，它会出现在脱敏后的堆栈中。数据库不可用时，完整脱敏堆栈仍输出到应用日志。无可信企业归属的签名/JSON错误只写应用日志，不伪造企业业务日志。

## 兼容与发布

先执行 `sql/sync-batch-logging.sql`，再发布 `dj-admin/target/dingKingdee.jar` 和后台前端。迁移仅新增字段和分页表，旧版服务可继续写旧字段。

现有历史记录标记为PAGE，保留原每页口径，不回填或猜测历史批次。升级时仍在使用数字nextToken的旧同步任务标记为LEGACY，只汇总升级后能够关联的续传部分；重新发起同步即可得到完整BATCH日志。接口调用增加page_id关联。

本次数据库迁移已执行，保留3426条历史单页日志；执行记录见 `output/sync-batch-migration-result.json`，迁移前结构见 `output/sync-batch-schema-before.json`。没有重启或发布远程服务。
